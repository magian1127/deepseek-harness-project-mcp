# 行为契约（behavior）

> 本文件是 `.mcp.json` 语义、传输支持、命名规范化、信任模型与控制台（按钮/弹层）的**唯一权威位置**。
> 面向用户的概览见 [`../README.md`](../README.md)；实现规则见 [`development.md`](development.md)；
> 设计依据见 [`design.md`](design.md)；按症状诊断见 [`troubleshooting.md`](troubleshooting.md)。

## 1. 适用范围

本插件让**项目根目录**的 `.mcp.json` 决定该项目下的会话启用哪些 MCP 服务器。

- **项目根**：从会话工作区（`session.header.cwd`）向上找到的第一个含 `.git` 的目录；
  一路到文件系统根都没有 `.git` 时，用工作区目录本身。
- **项目级服务器**：由 `.mcp.json` 声明、本插件按会话挂载的服务器。它们与 profile 里的
  **全局 MCP 行**是两套东西（见 §8）。
- **作用域**：每个会话按自己的工作区独立判定。同一进程里两个会话可以各自挂载不同的项目
  服务器；反过来，同一个项目在 N 个会话下就是 **N 份连接与子进程**。
- **子代理不挂载**：`origin === 'subagent'` 的会话被跳过（子代理与父会话共享工作区，
  重复建连接与子进程没有意义）。
- **分叉会话照常挂载**：分叉会话（fork）的 header 里也有 `parentSession`，但**不带**
  `origin`，是独立会话，因此与普通会话同样参与挂载判定。判据只有 `origin` 一条。

## 2. `.mcp.json` 的读取与解析

输入采用 Claude Code 约定格式：

```json
{
  "mcpServers": {
    "<服务器名>": { ... }
  }
}
```

解析结果与后续行为：

| 文件状态 | 行为 |
| --- | --- |
| 文件不存在（含任何读取失败，例如权限不足） | **静默跳过**，不挂载、不提示 |
| 文件大于 1 MiB | 不读取、不挂载；控制台报"过大"并给出实测大小与上限（见下） |
| 不是合法 JSON | 不挂载；控制台显示原因 |
| 顶层不是 JSON 对象（数组、字符串、数字、`null`） | 同上 |
| `mcpServers` 缺失 | 视为空（**不报错**）；控制台会说明这份文件没有声明任何服务器 |
| `mcpServers` 不是对象 | 不挂载；控制台显示原因 |
| 单条服务器条目非法 | 只跳过该条，其余照常挂载；原因在控制台可见 |

**尺寸上限 1 MiB**：读盘发生在会话创建的同步路径上，无上限的读取会让一个异常大的
`.mcp.json`（本插件的威胁模型正是"克隆陌生仓库并打开它"）在会话创建时耗掉大量内存。
上限在**读之前**按文件大小判定，超限即拒读（不读进内存），并**与"文件不存在"分开报告**——
报"没有 `.mcp.json`"会是假陈述，你也无从知道要把它改小。真实的 `.mcp.json` 只声明服务器
列表，远小于 100 KiB，1 MiB 留了两个数量级余量，不会误伤合法文件。

诊断文本只说明"哪里不对"（路径 + 原因），**不回显文件内容**——`.mcp.json` 可能含凭据，
而 `JSON.parse` 的错误消息本身会回显原文片段。

## 3. 条目字段语义

| 输入形状 | 输出传输 | 备注 |
| --- | --- | --- |
| `{command, args?, env?}` | `stdio` | `cwd` = 会话工作区（不是项目根） |
| `{type: "stdio", command, args?, env?}` | `stdio` | 显式写法，等价 |
| `{type: "http" \| "streamable-http", url, headers?}` | `streamable-http` | `http` 是 `streamable-http` 的别名 |
| `{type: "sse", url}` | **跳过** | DSH 不支持，见 §4 |
| `{type: "ws", url}` | **跳过** | DSH 不支持 |
| `{type: "sdk"}` | **跳过** | 仅 SDK 宿主可注册 |
| `{url}` 但无 `type` | **跳过** | 无法判断传输类型；它会被误读为 stdio 并因缺 `command` 而失败 |
| `type` 不是字符串 | **跳过** | 只支持字符串字面量 |

字段级约束：

| 字段 | 约束 | 违反时 |
| --- | --- | --- |
| `command`（stdio） | 必须是非空字符串，**展开后也必须非空** | 跳过该条 |
| `args` | 必须是字符串数组；缺省为 `[]` | 跳过该条 |
| `env` | 必须是"字符串 → 字符串"的对象；缺省为 `{}` | 跳过该条 |
| `url`（HTTP） | 必须是非空字符串，**展开后也必须非空** | 跳过该条 |
| `headers` | 必须是"字符串 → 字符串"的对象；缺省为 `{}` | 跳过该条 |
| `serve`（HTTP，可选） | 见 §3.2 | **只丢弃 `serve`**，该条仍挂载 |
| 条目本身 | 必须是 JSON 对象 | 跳过该条 |

"展开后也必须非空"是独立于字段类型检查的一道复查：`"command": "${CMD:-}"`（或 `CMD`
本身是空串）展开后得到空串，而下游 schema 只要求字符串、不校验非空——空 `command` 会
一路走到 `spawn('')` 才抛错，只落一条日志，服务器却已被列为已挂载。因此展开为空串时
按上表**跳过该条**并在控制台弹层说明。`env` / `headers` 的键与值按普通数据键处理：
键名 `__proto__` 在**本插件内**不会被丢弃——`translate.ts` 与 `config-guard.ts` 都按普通
数据键处理它。但它**到不了服务器**：下游 `mcp-client` 的 Config schema 在 Cordis 规范化时
用朴素赋值重建字典（`vendor/schemastery/src/index.ts:790-792` 的 `result[rKey] = ...`），
该键名会命中原型 setter 而被静默丢弃。完整链路与实测见
[`design.md` 第 10 节](design.md#10-环境变量展开与凭据)。

`env` 是**附加**环境变量，不是替换：服务器进程继承宿主环境，再叠加这里给出的键。

### 3.1 变量展开

`command`、`args` 的每个元素、`env` 的**键与值**、`url`、`headers` 的**键与值**都支持：

| 写法 | 语义 |
| --- | --- |
| `${VAR}` | 取变量 `VAR` 的值 |
| `${VAR:-default}` | `VAR` 已定义时取其值，否则取 `default` |
| `${VAR:-}` | `VAR` 已定义时取其值，否则取空串（用于"可选但可留空"的凭据） |

判定与边界：

1. **只认自有属性**：`env` 里存在该名字（且不为 `undefined`）即算"已定义"。
   原型链成员（`toString` / `constructor` / `valueOf` 等）**不算**已定义——否则
   `.mcp.json` 里字面写 `${toString}` 就会把一段 JS 源码展开进 `command` / `url` / `env`。
2. **空串是已定义的值**：`VAR=''` 时 `${VAR:-default}` 取**空串**，**不**取 default。
   这与 bash 的 `${VAR-default}`（不带冒号）一致，与 `${VAR:-default}`（带冒号）不同。
   理由：空串通常是用户显式设置的结果，静默替换成 default 会掩盖配置意图。
3. **变量未定义且无默认值** → 跳过该服务器，诊断只报**变量名**，不报值。
   理由：带未展开的 `${VAR}` 字面量启动，几乎必然导致认证失败且错误难以理解。
4. 多处缺变量时只报**第一个**（诊断要短，多变量名没有增量信息）。
5. 变量名沿用 POSIX 形状 `[A-Za-z_][A-Za-z0-9_]*`；不匹配的 `${...}` 原样保留，不展开。
6. 展开只在内存中进行，不落盘、不入日志、不入会话记录。

### 3.2 `serve`：HTTP 条目的按需拉起（可选）

HTTP 模式下 DSH **不启动任何子进程**——它只向 `url` 发 HTTP 请求，服务必须由外部启动。
服务没在跑时 DSH 连不上、工具不可用，而用户看不出为什么。`serve` 让插件在这种情况下
**把服务拉起来**，等服务就绪再把条目交给 `mcp-client`。

```json
{
  "type": "http",
  "url": "http://127.0.0.1:19701/mcp",
  "serve": {
    "command": "dotnet",
    "args": ["<path>/MudBlazor.Mcp.dll", "--version", "9.10.0"],
    "env": { "ASPNETCORE_URLS": "http://127.0.0.1:19701" },
    "health": "http://127.0.0.1:19701/health/ready",
    "readyTimeoutMs": 120000
  }
}
```

| 字段 | 必填 | 语义 | 违反时 |
| --- | --- | --- | --- |
| `command` | ✅ | 可执行文件。与 stdio 的 `command` 同语义（含 `${VAR}` 展开） | 丢弃 `serve` |
| `args` | ❌ | 参数数组，默认 `[]`。支持 `${VAR}` 展开 | 丢弃 `serve` |
| `env` | ❌ | **追加**环境变量（宿主环境之上叠加），键与值都支持 `${VAR}` 展开 | 丢弃 `serve` |
| `health` | ❌ | 就绪检查 URL。只允许 `http://` / `https://`。省略时用 `url` 的 **origin** + `/health/ready` 推导 | 丢弃 `serve` |
| `readyTimeoutMs` | ❌ | 等待就绪的上限（毫秒），默认 **120000**（120 秒）。只接受有限正数 | 退回默认并记日志 |

**`serve` 畸形只丢弃 `serve`，该条服务器照常挂载。** 这与 `headers` / `args` 的处理刻意
不同：那两者形状不对会让**连接本身**与预期不符，继续挂载只会带来更难诊断的故障；而
`serve` 是纯粹的辅助——它的全部作用是"服务没在跑时帮忙拉一把"。畸形时丢掉它、记一条
只含**字段名与变量名**的日志（绝不回值），然后照常挂载：服务若已被你手动启好，一切正常；
若没启，症状就是"服务不可达"，而那条日志正好解释了原因。反过来让整条 HTTP 条目消失，
会把"辅助功能的配置写错了"升级成"这个服务器完全用不了"。

#### 执行流程

挂载一个 HTTP 条目时：

```
1. 健康检查（GET health，单次探测超时 2 秒）
   ├─ 成功 → 直接交给 mcp-client（零额外动作，serve 完全不被触碰）
   └─ 失败 → 走 2
2. 有 serve 字段吗？
   ├─ 没有 → 记一条日志，照常交给 mcp-client（让它自己重连）
   └─ 有   → 走 3
3. 拉起服务（脱离 DSH 的独立进程，见下）
4. 每 250 毫秒轮询 health，直到就绪或超过 readyTimeoutMs
   ├─ 就绪 → 交给 mcp-client
   └─ 超时 → 记一条日志，**仍交给 mcp-client**（让它自己重试；工具会注册但暂时不可用）
```

**`health` 推导失败（或 scheme 非法）时不拉起服务**，只记日志。理由：健康检查是拉起的
**唯一前提**——没有可用的健康端点就永远判不出"服务已经在跑"，于是每次会话挂载都会盲目
拉一次，重复实例只能靠端口占用失败收场，而那条失败是**静默的**（服务以 `stdio: 'ignore'`
启动，拿不到任何输出）。宁可不拉。

#### 等待行为：首条消息会等服务就绪

**这是 `serve` 唯一会让用户感知到的代价。** 挂载发生在 `agent/created` 里，而该事件是
serial 且被 await（DSH 的契约是"AgentLoop 在所有监听器结束前持有排队输入"）——因此
**该会话的第一条消息会等到服务就绪**，工具在首次请求前就注册好。这正是"等服务就绪再连"
的实现方式。

等待有明确上限（`readyTimeoutMs`，默认 120 秒），且**失败不抛**：超时后照常挂载，由
`mcp-client` 自己重连。等待**只影响该条目自己**——同一会话里其余服务器（尤其是 stdio
条目）照旧立即挂上。

为什么默认是 120 秒而不是常见的 30 秒：MudMCP 首次启动要克隆仓库并建索引，实测可超过
90 秒。偏长的代价只是首次打开某个项目时多等一会儿，偏短的代价是服务明明在正常启动却被
判成失败。上限另有一层硬收敛（30 分钟），因此 `.mcp.json` 里写一个极大的值也不会让会话
创建无限期卡住。

#### 进程生命周期归服务自己

拉起的服务是**脱离 DSH 的独立进程**：不继承任何管道、启动后立即丢弃引用。插件**不** kill 它、
**不** await 它退出、**不**监听它的 exit 事件。因此：

- 多个 DSH 实例（或 DSH 重启）复用同一个服务；
- DSH 关闭后服务仍在跑，由它自己决定何时退出（空闲自退）。

"脱离"的具体手段**按平台与命令**不同：

| 平台 | `serve.command` | 手段 |
| --- | --- | --- |
| POSIX | 任意 | 以新进程组启动（`detached`） |
| Windows | PowerShell（`pwsh` / `powershell`） | **不**用 `detached` |
| Windows | 其他（`dotnet` / `node` / …） | 用 `detached` |

因为这两件事在 Windows 上互斥：`detached` 会被 Node 实现成 `DETACHED_PROCESS`（子进程没有
控制台），而 PowerShell 在那种情形下**立刻以退出码 0 结束、一行都不执行**——`serve.command`
写成 `pwsh` 时服务根本起不来，插件还要白等满 `readyTimeoutMs`；反过来，不用 `detached` 的子
进程会挂在宿主控制台上，控制台被拆除（Ctrl+C、关掉终端）时一起被带走，直接 spawn 的服务就
活不过 DSH。Node 无法表达两全的 `CREATE_NO_WINDOW`，所以只能按命令分流。

对 PowerShell 那条路径，"服务活过 DSH"仍然成立，但**取决于启动脚本怎么创建服务**：由
`Start-Process -WindowStyle Hidden` 这类方式创建的进程没有控制台，因此免疫（已实测）；若脚本
把服务直接跑在自己前台，服务会随宿主控制台一起结束。实测矩阵与全部依据见
[`design-http-serve.md` §4.3](design-http-serve.md)。

**前提**：这条依赖"DSH 自身不在 Windows Job 对象里"。当前 DSH 由 explorer 这类普通父进程
启动、不在 Job 里（已实测）。若将来 DSH 被放进 Job（例如由某个 IDE 或计划任务启动），脱离
可能失败，届时需要退化为 `CREATE_BREAKAWAY_FROM_JOB` 之类的方案，或接受"服务随 DSH 退出"。
详见 [`design-http-serve.md` §4.3](design-http-serve.md)。

#### 并发与端口

两个会话同时挂载同一个 `url` 时，**只拉起一次**：插件按 `url` 维护"进行中的启动表"，
后到的会话等前一个的启动结果，而不是再拉一个（第二个会因端口占用失败）。去重按 `url`
而不是服务器名——冲突的根源是端口，同一个服务可能被两个项目用不同的名字指向。

若端口已被**别的**进程占用，拉起会失败：记一条日志（含服务器名与错误类型名），照常交给
`mcp-client`（它可能连上那个别的实例）。**不**检查端口归属，也**不**重试。

#### 安全

- `serve.env` 展开后的值**永不**进入日志、错误消息、会话记录或任何持久化产物（红线 3）；
  诊断只记服务器名、字段名与变量名。
- `serve` 是本插件自己的字段，**不是** `mcp-client` 的配置项，挂载前会被剥离——它绝不会
  到达 `ctx.plugin()`。
- `command` / `args` 来自已批准（指纹绑定）的 `.mcp.json`，直接 exec，**不经 shell 解释**。
- `health` 只允许 `http://` / `https://`：`fetch` 还支持 `file:` / `data:` 等，放行它们
  等于让一份克隆下来的仓库配置指挥本插件去读本机文件。

## 4. 传输支持矩阵

| 传输 | 支持 | 依据 |
| --- | --- | --- |
| `stdio` | ✅ | DSH `createTransport` 的 `stdio` 分支 |
| `streamable-http`（含别名 `http`） | ✅ | DSH `createTransport` 的 `streamable-http` 分支 |
| `sse` | ❌ 跳过 | DSH 的 `createTransport` 是封闭 switch，只有上面两个分支 |
| `ws` | ❌ 跳过 | 同上 |
| `sdk` | ❌ 跳过 | 仅 SDK 宿主可注册 |

MCP TypeScript SDK 2.0 确实导出 `SSEClientTransport`（已标记 deprecated），但支持它必须改
DSH 源码，超出"只加插件"的范围。实际影响很小：SSE 已被 MCP 规范废弃，主流服务器都提供
`streamable-http`。

## 5. 服务器命名与工具名映射

`serverName` 必须匹配 `/^[A-Za-z0-9_-]{1,32}$/` 且在同一会话的注册作用域内唯一。

`.mcp.json` 的键允许其他字符，因此需要规范化：

1. 已匹配该模式 → **原样使用**（既有工具名不变）。
2. 不匹配 → NFKD 规范化 → 非 `[A-Za-z0-9_-]` 的字符替换为 `_` → 去掉首尾 `_` →
   截断 20 字符 → 若结果为空则用 `server` → 追加 `_` + **原始键名**的 sha256 前 8 位。
3. 哈希基于**原始键名**而非 slug：否则 `a b` 与 `a  b` 会得到同一结果并在同一作用域内撞名。
4. 同一文件内规范化后重名 → **先到者胜**，后者跳过并在控制台弹层说明。

例：键 `my server!` → 规范化后形如 `my_server_<8位哈希>`。

**工具名映射**：服务器的工具以 `mcp__<serverName>__<toolName>` 出现。重命名过的服务器用
**规范名**，因此控制台会同时显示原名与规范名——照着规范名去批准或去工具列表里
查找。

规范化是稳定的：同一键名始终得到同一结果，重启与重开会话不会改变工具名。

## 6. 信任模型

### 6.1 存储

`${DSH_HOME:-~/.dsh}/project-mcp-trust.json`，权限 `0600`，原子写 + 文件锁
（`@deepseek-ai/dsh-atomic-write` 可用时；不可用时降级为"同目录临时文件 + rename"，
仍是原子替换，只失去跨进程串行化）。

```json
{
  "version": 2,
  "projects": {
    "<项目根路径>": {
      "servers": {
        "github": { "approvedAt": "2026-10-06T12:00:00.000Z", "configHash": "sha256:<hex>" },
        "memory": { "approvedAt": "2026-10-06T12:00:00.000Z", "configHash": "sha256:<hex>" }
      }
    }
  }
}
```

批准粒度是**服务器 × 该条目的配置哈希**（v2）。挂载时逐条比对：同名服务器只有配置哈希
命中才算已批准，因此文件里新增的服务器不会因为旧批准而生效，改 A 也不再连累 B 的批准。

### 6.2 配置哈希语义

`configHash` 是 `sha256(规范化后的条目 JSON)`，形式 `sha256:<hex>`。输入是该服务器在
`.mcp.json` 里的**字面量**条目对象——**不含**任何展开后的环境变量值（展开只发生在挂载/
拉起时，结果永不落盘）。

**规范化**：解析后按 key 字典序递归序列化，数组保序，剔除空白与键序这类纯格式差异。

因此：

| 对该条目的变更 | 是否改变哈希 |
| --- | --- |
| 调整缩进、换行、键的顺序 | **不改变**（不需要重新批准） |
| 改任何值（`command` / `args` / `url` / `env` 字面量…） | **改变**（必须重新批准） |
| 增删条目、改服务器名 | **改变**（新名字下没有记录，必须重新批准） |
| `git pull` 拉入新服务器 | 新服务器**需重新批准**；未变化的服务器批准**保留** |
| 加入 `__proto__` 键 | **改变**（该键被当作普通数据键保留，不会被丢弃） |
| `env` / `headers` 里的 `__proto__` 键 | 同上：哈希把它算在内、本插件不丢弃它；但下游 schema 规范化时会丢（见 §3 与 `design.md` §10），因此**批准的内容与服务器实际收到的内容不一致** |
| 嵌套深度超过 64 层 | 降级为对**原文**取哈希（仍对内容敏感，只是格式差异也会要求重新批准） |

最后两条是刻意的保守降级：偏保守的方向只会多要求一次批准，不会让内容变更逃过哈希。

### 6.3 失败关闭

信任文件缺失、JSON 损坏、版本号不认识、任一项目条目结构不符 → 一律视为**全部未信任**，
不阻止 DSH 启动，不抛异常。本插件运行在会话创建路径上，抛异常会中断会话。

**version 1 的旧文件同样读为全部未信任**：v1 只存整文件指纹、不存内容，展开不出
per-server 哈希，因此**不做迁移**——升级到 v2 后每个项目需在控制台重新点一次"启动"。
下一次批准会把整个文件按 v2 原子重写，旧状态随之消失。

### 6.4 仓库无法自我批准

信任存储只存在于 `${DSH_HOME:-~/.dsh}`，项目内**没有任何可写入的批准通道**——`.mcp.json`
是只读的，项目里也不存在第二个被本插件读取的批准文件。克隆一个陌生仓库并打开它，不会
执行其中的任何命令。

### 6.5 为什么批准必须是用户动作

批准只能由用户在控制台点"启动"产生：会话创建时没有 open turn，宿主审批服务只在 turn 内
可用，无法在创建时弹窗确认；而系统提示词也不承载"请批准"这类需要用户行动的信息（见 §9）。
仓库内始终没有任何可写入的批准通道，因此克隆陌生仓库并打开它，不会执行其中任何命令。

## 7. 控制台（按钮与弹层）

命令面已删除：`/mcp-project` 不再注册，也没有任何等价的斜杠命令。状态与操作全部在 Web
GUI 的输入区，两个面：

| 面 | 位置 | 内容 |
| --- | --- | --- |
| 按钮 | composer 工具行（`conversation.input.left`） | 插头图标 + 状态文字（「检测中」/「N 个未启动」/「MCP 就绪」）；完整文案在 tooltip |
| 弹层 | 按钮上方锚定面板（按钮组件内联渲染，fixed 定位） | 逐服务器一行：名称（含规范化原名）、传输、状态、原因、动作 |

弹层与权限菜单同款 dismiss 行为：点击弹层外、按 Esc、窗口缩放都会关闭；动作点击后弹层保持
打开，状态行经轮询（1.5s）自动更新。刻意不挂 `shell.overlay`：那是 root 作用域（拿不到会话），
且上一版跨组件共享开关状态曾导致弹层无法关闭。

按钮**每会话**渲染，但状态来自"工作区级计划 + 会话级挂载记账"的合成；状态变化秒级反映，
不需要重开会话。

### 7.1 按钮取态

| 情形 | 按钮 |
| --- | --- |
| 工作区没有可用的 `.mcp.json` 计划 | **不渲染**（保持"不打扰"） |
| 计划检测中（会话刚创建 / 文件刚变化） | 图标 + 转圈 |
| 需动作数 N > 0 | 图标 + 「N 个未启动」 |
| N = 0 且计划非空 | 图标 + 「MCP 就绪」，仍可点开查看与撤销 |

**需动作数 N** = `未授权` + `失败` + `本会话未挂载`。`启动中` 只转圈、不计数，且转圈不会
永久停留（挂载被拒绝即转 `失败`）。

### 7.2 弹层行

| 状态 | 含义 | 动作 |
| --- | --- | --- |
| `未授权` | 条目在文件里，但信任记录没有它（或配置哈希已变） | [启动] |
| `启动中` | 正在拉起服务，或挂载尚未结算 | — |
| `已挂载` | 本会话已挂上（工具名 `mcp__<名称>__*`） | [撤销授权] |
| `本会话未挂载` | 已授权但本会话没挂上：插件换血（删除→安装），或批准发生在会话创建之后 | [启动]（在**本会话**补挂，无需重开会话） |
| `失败` | 挂载 fiber 被拒绝或注册同步抛错（只记错误类型名） | [重试] |
| `已跳过` | 传输不支持 / 变量缺失 / 与全局行撞名 / 规范化重名 | — |

文件级问题（无法解析、超过 1 MiB）没有逐行状态：弹层顶部给一行原因，并计入需动作数
（否则用户不知道要点开看）。诊断只含服务器名、字段名与错误类型名，**不含** `.mcp.json`
内容与任何展开后的变量值。

### 7.3 动作语义

- **[启动]** = 授权该服务器的**当前配置**（写 §6.1 的 per-server 记录）+ 异步挂载/拉起。
  批准是持久的：同一项目此后所有会话直接挂载，只有该服务器的配置变了才重新需动作。
- **[重试]** 与 [启动] 同源（配置未变时不重复写批准，直接重挂）。
- **[撤销授权]** 删除该服务器的批准记录，并卸载本会话已挂的对应实例。
- **幂等**：同一会话重复启动同一服务器不会重复挂载（同名已挂则跳过）。
- **两条挂载入口共用同一守卫**：`agent/created` 的自动挂载与控制台的启动都走 `mountInto`
  的 Config 自校验，非法配置都拦在 `ctx.plugin()` 之前（§10）。
- **会话不可寻址时如实回空**：桥接查不到该会话就回"无视图"，绝不编造一个状态。

### 7.4 无 Web UI 的环境

headless / SDK 等没有 `webServer` 或没有 Client 的 profile 上不存在控制台，因此**没有批准
入口**——那里只剩 Host 日志。这是刻意的非目标（§13），不提供替代 UI 或命令行。

### 7.5 计划与实际是两套口径

`已挂载` 取自**本会话的真实挂载记账**（插件侧按会话 id 键控的 `serverName` 集合），而不是
计划：计划回答"按当前信任状态应当挂什么"，视图回答"现在什么是活的"。两者可以合法地不一致，
因此视图分别呈现、互不代言：

- **计划要挂但本会话没挂** → 行状态 `本会话未挂载`（计入需动作数）。最常见的是**别的会话**
  批准之后本会话才创建，或插件在会话存活期间被换血。
- **本会话挂了但计划已不含它** → 仍显示 `已挂载`：`.mcp.json` 在挂载之后被改动或删除时，
  先前挂上的实例依然在跑。

**未授权项不会因为未授权而从弹层消失**：即使一条都没批准，弹层也列出全部可挂载服务器与
全部跳过原因——用户最需要诊断信息的时刻恰恰是批准**之前**。

## 8. 与全局 MCP 行的关系

**全局行**指 profile 补丁（bundle patch、profile 自己的 `cordis.patch.yml`、home 级
`cordis.patch.yml`、`--patch` 覆盖层）里声明的 `mcp-client` 行。它们由 DSH 在进程启动时
挂载，不受本插件管辖。

### 8.1 撞名检测口径

本插件在**每次会话创建时**按需遍历 Loader 树，收集所有 `mcp-client` 行的 `serverName`：

- **模块名精确匹配** `@deepseek-ai/dsh-mcp-client`。行名写成子路径（如
  `@deepseek-ai/dsh-mcp-client/something`）或相对路径时**漏检**——那种写法不是 DSH 声明
  MCP 行的常规形式，但若你确实这样写，撞名保护不会生效。
- 只看 `config.serverName` 是否为**非空字符串**；缺失或非字符串的行被忽略。
- 遍历 Loader **本体**（`entries()` 在 Loader 上，不在 `loader.root` 上），并下降嵌套子树。
- 任何一步失败（形状不符、`entries()` 抛错）都降级为**空集**而非半份名单：残缺名单会被
  当成完整名单，让部分项目服务器静默遮蔽全局服务器。空集是"无法判定"的表达。
- `ctx.get('loader')` 取不到 Loader 时（未挂载 Loader 的宿主）名单同样是空集，但这种情况
  会**额外记一条警告日志**——静默的空集会伪装成"没有任何全局行"。
- **不缓存**：Loader 没有覆盖"已有条目改配置"的事件，缓存会在 HMR 改配置后失效。

### 8.2 处理：跳过项目侧

`.mcp.json` 里的服务器若与全局名单撞名 → **不挂载**，控制台报告"与全局 MCP 行
同名，已被全局配置提供，跳过"。

为什么不警告后仍挂载：agent 作用域的同名服务器会**静默遮蔽**全局的，且会额外 spawn 一个
子进程。跳过比遮蔽更符合"全局有的本地就不要启动了"。

### 8.3 已知局限 被禁用的全局行仍占名

检测只看行的模块名与 `serverName`，**不看该行是否被禁用**。后果：

- 一条 `disabled: true` 的全局行仍会被计入全局名单；
- 同名的项目服务器因此被当作"已被全局配置提供"跳过；
- 而全局侧实际不连接 → **两边都不挂载**。

这是当前实现的已知局限。绕过方式：给项目服务器换一个不与禁用行同名的键，或启用/删除
那条全局行。

**为什么不修**：读条目的 `disabled` 属性会触发 `!!js` 表达式求值（`new Function` + `eval`），
在会话创建路径上执行用户配置的 JS，与本模块"只读、不求值"的姿态冲突。安全的修法是只判
`entry.options.disabled === true` 字面量，尚未实施。

### 8.4 能力边界

插件**能检测到**全局行（遍历 Loader 树取它们的 `serverName`），但这份名单**只用于撞名过滤**，
**不会向你提示**；插件也**无法阻止它们连接**——它们挂载得比任何会话创建都早得多。
profile 里仍有 MCP 行时，它们在 DSH 启动时就会连接并 spawn 子进程，与本插件无关。

**为什么不提示**：插件无法阻止那些行连接，你唯一能做的是改 profile 补丁，而那已经超出本插件
的管辖范围（它只管项目根的 `.mcp.json`）。为一条你无能为力的信息在启动时打扰你，收益为负，
因此这里如实描述为"能检测、不提示"。

## 9 不注入系统提示（G4）

本插件**从不**往系统提示词写任何内容。提示文本会占用模型上下文，而"这里有 MCP 需要你
批准"属于界面信息、不是模型信息：

| 计划状态 | 会话提示（系统提示词） |
| --- | --- |
| 文件不存在（`skip`，静默） | 无 |
| 会话没有工作区 / 子代理 / 服务器全部被跳过（`skip`） | 无 |
| 文件无法解析（`invalid`） | **无** |
| 有可挂载项但未批准（`untrusted`） | **无** |
| 已批准（`mount`，含 `configs` 为空） | 无 |

**任何计划状态下，本插件都不往系统提示词里写一个字**（目标 G4）。提示词是模型的上下文，
"这里有 MCP 需要你批准"属于用户界面信息，不该占用它，也不该由插件替用户决定它值得占用。

需要用户行动的信息全部走控制台：按钮的状态文字 + 弹层的逐行状态与原因（§7）。诊断（每条
服务器的跳过原因、规范化重命名、`mcpServers` 缺失、"文件里没有可用服务器"）同样只在弹层
里出现，不打扰会话。

## 10. 挂载语义

- **挂载点是会话的 agent 作用域**，不是宿主：项目级 MCP 必须按会话生效，挂到宿主上会让
  第一个会话的项目服务器泄漏给所有会话。
- **不等待连接**：`ctx.plugin(...)` 后立即返回，会话秒开。代价是**首条消息可能赶不上工具
  注册**——模型当轮看不到这些工具，下一轮即可见（工具注册会触发 `tools/change`）。
  **例外**：配了 `serve` 的 HTTP 条目会先等健康检查（有明确上限、失败不抛），见 §3.2
  ——那是"等服务就绪再连"，与"await MCP 握手"是两件事，后者仍然不做。
- **启动失败不影响会话**：挂载时设 `failOnStartupError: false`，坏服务器只记日志。
  这与 ACP 的 `failOnStartupError: true` 相反——ACP 要工具必定就位，本插件要会话必定成功。
- **启动失败即从挂载记账移除**：fiber 以启动失败拒绝（连接失败、工具同步失败、重名等）时，
  该服务器会**立即从本会话的挂载记账里摘掉**，并记一条"已从挂载记账移除"的日志。失败的
  fiber 停在 FAILED 状态，实例并没有活着，因此控制台不再把它显示为 `已挂载`，而是显示为
  `失败`（并计入需动作数）——`已挂载` 的全部职责就是回答"现在什么是活的"。
  摘除按**身份**（引用）而非名字：同名条目若已被后来者替换，迟到的旧拒绝不会误删新条目，
  也不会把活着的实例标成失败。
- **每会话独立连接**：N 个会话 = N 份连接与子进程。全局行只有一份（进程级），这是本插件
  只接管项目级服务器的原因之一。
- **命令行带会话标记**：stdio 服务器在 `.mcp.json` 给出的 `args` **之后**追加
  `--project-mcp-session <SessionId>`（`SessionId` 即 `agent.id`，也是该会话的会话 id）。
  同一份 `.mcp.json` 在多个会话下产出的命令行其余部分**逐字相同**（`command`、`args`、
  `cwd` 全部一致），这段标记是分辨"哪个进程属于哪个会话"的唯一手段（诊断方法见
  [`development.md`](development.md#8-验证分层与未验证项)）。标记**只含会话 id**，不含
  任何配置内容——进程命令行对本机所有用户可见。
  服务器忽略未知参数，因此不影响运行、也不改变工具面。`streamable-http` 没有子进程，
  不追加（也没有 `args` 字段可放）。分辨进程归属的具体命令见
  [`development.md` §8.2](development.md#82-诊断分辨一个-mcp-子进程属于哪个会话)。
- **同一会话只挂一次**：挂载记账按 **`agent.id`（会话 id）** 键控，因此同一个会话被
  `agent/created` 报告两次（哪怕每次传的是不同的 agent 对象）也只挂一次。会话身份是
  id 而不是对象引用——按对象引用记账会让第二次报告建出空记账、绕过幂等判定，从而多挂
  一个实例、**多 spawn 一个命令行相同的子进程**。
- **可逆**：挂载与桥接注册（路由、index 注入、监听器）都随会话销毁、插件卸载（含换血重载）
  回收，两条路径各自独立且可任意顺序重复执行。会话销毁的清理同样按会话 id 定位记账。
- **控制台的"启动"立即挂载**：批准之后服务器挂进当前 agent 作用域，无需重开会话。
- **执行不受 agent 沙箱约束**：MCP 服务器是项目提供的代码，批准后以子进程形式运行；
  这与 profile 里的全局行同性质。

### 10.1 批准后当前会话的状态

| 面 | 点"启动"后的行为 |
| --- | --- |
| 项目服务器挂载 | **立即生效**：挂进当前 agent 作用域，无需重开会话 |
| 控制台按钮与弹层 | **秒级反映**：状态是活状态，经桥接流推送；`已挂载` 读的是**本会话真实挂载记账**，不是计划 |
| 系统提示词 | **始终为空**：本插件不注入任何内容（§9），批准后同样不会冒出"未启用"之类文本 |

需要留意的边界：**别的会话**批准后，本会话的计划同样变成"已批准"，但服务器不会自动挂进
本会话——挂载只发生在会话创建时或本会话自己在控制台点"启动"时。这种情况在弹层里显示为
`本会话未挂载` 并计入需动作数（见 §7.2），点一下即挂上。

## 11. 失败模式速查

| 症状 | 行为 | 去哪里看 |
| --- | --- | --- |
| 没有 `.mcp.json` | 静默跳过，按钮不渲染 | — |
| `.mcp.json` 大于 1 MiB | 不读取、不挂载 | 控制台弹层顶部一行（报实测大小与上限） |
| `.mcp.json` 解析失败 | 不挂载 | 控制台弹层顶部一行（原因） |
| `mcpServers` 缺失或为空对象 | 不挂载 | 控制台弹层（说明这份文件没声明服务器） |
| 单条服务器配置非法 | 只跳过该条 | 控制台弹层的 `已跳过` 行 |
| 传输不支持（`sse` / `ws` / `sdk`） | 跳过该条 | 控制台弹层的 `已跳过` 行 |
| 有 `url` 无 `type` | 跳过该条 | 控制台弹层的 `已跳过` 行 |
| 变量未定义且无默认值 | 跳过该条，只报变量名 | 控制台弹层的 `已跳过` 行 |
| `command` / `url` 展开后为空串 | 跳过该条（否则空 `command` 会到 `spawn('')` 才失败，却被列为已挂载） | 控制台弹层的 `已跳过` 行 |
| 配置不满足 `mcp-client` 的 schema（如上游新增必填字段） | **挂载前拦下**该条，不交给 `ctx.plugin()`；记一条只含服务器名与出错字段的日志，绝不回显配置内容 | DSH 日志 |
| `serve` 字段畸形（缺 `command`、`args` / `env` 形状不对、`health` scheme 非法等） | **只丢弃 `serve`**，该条服务器照常挂载；记一条只含字段名与变量名的日志 | DSH 日志 |
| `serve.readyTimeoutMs` 非法或超上限 | 退回默认 120000（超上限则收敛为 30 分钟）并记日志 | DSH 日志 |
| HTTP 条目的服务不可达，且**没有** `serve` 配置 | 不拉起，记一条日志，照常交给 `mcp-client`（它自己重连） | DSH 日志 |
| HTTP 条目的服务不可达，有 `serve` | 拉起服务并轮询健康端点；就绪后交给 `mcp-client` | DSH 日志 |
| 拉起后等待就绪超时（默认 120 秒） | 记一条日志，**仍交给 `mcp-client`**（工具会注册但暂时不可用） | DSH 日志、控制台（该条显示为未连接并计入需动作数） |
| 拉起服务失败（端口被别的进程占用等） | 记一条日志（含错误类型名），照常交给 `mcp-client`（可能连上别的实例） | DSH 日志、控制台 |
| 规范化后重名 | 先到者胜，后者跳过 | 控制台弹层的 `已跳过` 行与行内原名 |
| 与全局行撞名 | 跳过项目侧 | 控制台弹层的 `已跳过` 行 |
| 配置哈希不匹配（该条目被改过） | 不挂载，回到未授权 | 控制台弹层的 `未授权` 行 |
| 信任文件损坏 / 版本不认识（含 v1） | 全部未信任，不阻止启动 | 控制台弹层（全部显示 `未授权`） |
| MCP 连接失败 | 只记日志，不影响会话；该服务器**立即从挂载记账移除** | DSH 日志、控制台（`失败` 行） |
| 拿不到 `mcp-client` 模块 | 不挂载（安全侧），记错误日志；控制台仍可检视状态 | DSH 日志 |
| `webServer` 服务缺席（无 Web GUI 的 profile） | 控制台不存在，只剩 Host 日志；挂载与批准语义不变（但没有批准入口） | DSH 日志 |
| profile 里仍有 MCP 行 | 不受管辖，启动时即连接 | — |

## 12. 数据边界

| 数据 | 位置 |
| --- | --- |
| 信任记录（版本、项目根、每台服务器的批准时间与配置哈希） | `${DSH_HOME:-~/.dsh}/project-mcp-trust.json`，权限 `0600` |
| `.mcp.json` | 项目根目录，**只读**，本插件不写入 |

不落盘、不入日志、不入会话记录、不入错误消息：`.mcp.json` 的内容、展开后的环境变量值。
诊断只含服务器名、变量名与自造的原因文本。

## 13. 非目标

明确不做（YAGNI）：

- 不支持 `ws` / `sse` 传输。
- 不做 OAuth 流程。
- 不做跨工作区的集中管理页（控制台只回答"这个会话的项目里有什么"）。
- 不接管 profile 里的全局 MCP 行。
- 不做 `.mcp.json` 的写入或管理。
- 不为无 Web UI 的 profile 提供替代批准入口（那里只剩 Host 日志，见 §7.4）。
- **不管被拉起服务的生命周期**：`serve` 只负责"服务没在跑时拉一把"，拉起后不 kill、不监控、
  不重启、不回收。服务何时退出由它自己决定（见 §3.2）。
