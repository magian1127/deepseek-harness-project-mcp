# 故障排查（troubleshooting）

> 本文件只负责"症状 → 诊断动作"。用户可见语义与失败模式见 [`behavior.md`](behavior.md)；
> 实现约束见 [`development.md`](development.md)；设计依据见 [`design.md`](design.md)。

## 快速分流

1. **先看输入区的控制台按钮**。它是诊断项目级 MCP 的唯一入口：点开后有项目路径、每台
   服务器的状态、未授权与已跳过项（含原因）、规范化重命名，以及 [启动] / [重试] /
   [撤销授权] 动作。没有 `.mcp.json` 时按钮不渲染（正常情形）。
2. 按钮**不渲染**就是"这个工作区没有项目级 MCP 可言"。**没有按钮也不代表别处没问题**——
   本插件从不往系统提示词写任何内容（G4），会话里不会出现任何 MCP 提示。
3. 确认运行中的进程加载的是新构建。Host 半边换血走**官方插件页删除 → 安装**（免重启，
   已实测）；`set_plugin` 停用→启用只修结构、**不**载入新构建。磁盘上的 `lib/` 不是运行时
   生效的证据。
4. 全程不要用"重启 DSH"代替诊断，也不要自行编辑受管 profile 行。

## 症状索引

| 症状 | 最短诊断路径 |
| --- | --- |
| 项目服务器一个都没挂上 | 控制台弹层看每行的状态：`未授权` → 点 [启动]；`已跳过` → 看逐条原因；弹层顶部有 fileNote → 见下 |
| **输入区按钮在，但弹层里一台服务器都没有** | 看 `<项目根>/.mcp.json` 的顶层是不是**直接写了服务器名**、漏了 `mcpServers` 包裹。旧构建按"零台服务器"静默处理（按钮在、点开空空如也且没有任何原因）；新构建已兼容顶层写法并记一条 warn，见 [`behavior.md` §2](behavior.md#2-mcpjson-的读取与解析)。处理：包一层 `{ "mcpServers": { … } }` |
| 工具列表里没有 `mcp__<名称>__*` | 先确认已批准（弹层里不是 `未授权`）；再看该服务器是否出现在 `已跳过` 里；最后看弹层该行是不是 `启动中`（后台挂载还没落定）——落定后下一轮再看 |
| 明明批准过，重开会话又要批准 | 配置哈希变了——`.mcp.json` 里**这台服务器**的条目有任何改动（含 `git pull` 改写它）都会失配。这是设计行为，见 [`behavior.md` 第 6.2 节](behavior.md#62-配置哈希语义) |
| 某个服务器被跳过，原因写着"与全局 MCP 行同名" | 该项目服务器与 profile 里的全局行撞名，项目侧不挂载。若那条全局行是 `disabled: true` 的，属于已知局限，见下 |
| 某个服务器被跳过，原因写着"不支持的传输类型" | `.mcp.json` 里写了 `sse` / `ws` / `sdk`。DSH 只支持 `stdio` 与 `streamable-http`（`http` 是别名） |
| 某个服务器被跳过，原因写着"变量 X 未定义且无默认值" | 该环境变量在 DSH 进程的环境里不存在。用 `${X:-默认值}` 提供回退，或在启动 DSH 的环境里设置它 |
| 某个服务器被跳过，原因写着"条目含 url 但没有 type" | 补上 `"type": "http"`（或 `"streamable-http"`） |
| 服务器名与预期不符，工具名前缀是 `mcp__my_server_ab12cd34__*` | 键名含 `[A-Za-z0-9_-]` 以外的字符，被规范化重命名。控制台弹层的行会同时给出原名 → 规范名 |
| 批准时报"未知的服务器名" | 只能用**规范化后**的名字批准（弹层行上显示的就是规范名）。原名含非法字符时不能直接用作批准名 |
| 批准成功但本会话没有挂载 | 该服务器被跳过（撞名 / 传输不支持 / 变量缺失 / 重名）。弹层的 `已跳过` 行给出原因 |
| 系统提示词里出现了 MCP 相关内容 | **不该发生**（G4：本插件从不注入系统提示）。若观察到，说明运行进程加载的是旧构建——Host 半边换血走官方插件页删除 → 安装，重启复查 |
| 已批准，但工具列表里没有 `mcp__<名称>__*` | 本会话没挂上：别的会话批准后本会话才打开，或插件在会话存活期间被换血。弹层把它显示为 `本会话未挂载` 并计入徽标——点 [启动] 即在本会话挂上 |
| 服务器已挂载但工具报连接失败 | MCP 服务器自身的启动或握手失败。挂载刻意不等待连接（会话秒开），失败只记日志，不影响会话。**该服务器会立即从挂载记账移除**，控制台把它显示为 `失败` 并计入徽标。查 DSH 日志与该服务器的 `command` / `url` 是否可手动执行 |
| 输入区没有控制台按钮 | 工作区没有 `.mcp.json`（正常），或 Client 半边未供应（**首次**供应需要重启一次 DSH——宿主模块表按进程缓存"非 client 包"），或该 profile 没有 `webServer`（headless / SDK，无控制台） |
| **桌面版**看不到输入区 MCP 按钮，**Web 版正常** | 旧构建的控制台路由用 boot 级 nonce，而桌面版页面文档由 Electron shell 直读打包 dist、`tapIndex` 永不执行 → `GET /project-mcp/status` 403 → 按钮静默隐藏。判据与修复见下"桌面版看不到按钮" |
| 按钮在但弹层打不开 / 状态一直是转圈 | 桥接路由未装上（`webServer` 晚于插件出现时有秒级重试，理论上自愈）；或 Client 半边是旧构建。查 DSH 日志，必要时删除 → 安装本插件换血 |
| 控制台弹层里出现"无法解析" | `.mcp.json` 不是合法 JSON、顶层不是对象，或 `mcpServers` 不是对象。修文件后弹层会在下次轮询自动更新 |
| 控制台弹层里出现"过大" | `.mcp.json` 超过 1 MiB，被**拒读**（没读进内存，也没挂载）。诊断给出实测大小与上限。这是有意的尺寸闸门：读盘在会话创建的同步路径上，无上限会让陌生仓库里的异常大文件拖住会话创建。精简该文件（真实的 `.mcp.json` 只需声明服务器列表，远小于 100 KiB）后重新批准 |
| 显示"未授权"但我不想批准 | 不用做任何事——不批准就不连接、不 spawn 进程。想让徽标消失就点 [启动] 授权，或把 `.mcp.json` 移出项目根 |
| 批准后想撤销 | 弹层里该行的 [撤销授权]：删除该服务器的批准记录，并卸载本会话已挂载的实例 |
| 撤销后重新批准没有生效 | 确认 `.mcp.json` 仍在原路径、该条目哈希未变；弹层应显示 `未授权`。若仍显示旧状态，确认运行进程加载的是新构建 |
| 信任文件损坏，所有批准都丢了 | 失败关闭行为：文件缺失、JSON 损坏、版本号不认识、条目结构不符 → 一律视为全部未信任。重新批准即可；插件不会阻止 DSH 启动 |
| 克隆陌生仓库后担心被自动执行 | 不会。批准记录只存在于 `${DSH_HOME:-~/.dsh}`，项目内没有可写入的批准通道；未批准时既不 spawn 进程也不发起网络连接 |
| 子代理会话里没有项目 MCP | 设计如此：子代理（`origin === 'subagent'`）与父会话共享工作区，不重复建连接与子进程。**分叉会话（fork）不属于此列**——它带 `parentSession` 但无 `origin`，是独立会话，照常挂载 |
| 多个会话各起了一份子进程 | 设计如此，**不是缺陷**：MCP 客户端挂在**会话作用域**里，工具的可见性、preset 与权限都按会话分层，一个连接没法同时属于两个会话。所以 N 个会话 = N 份连接与子进程（子代理会话贡献 **0 份**；同一会话被 `agent/created` 报告两次也只挂一次）。要全进程单份就把该服务器写进 profile 的全局行——代价是工具对**所有**会话可见，且不再受 `.mcp.json` 的逐项目批准模型管理 |
| 开新会话时 CPU 抖一下，任务管理器里出现 `MSBuild` / `VBCSCompiler` | 挂载的 `command` 是 `dotnet run --project …`：**每个会话挂载都是一次真实的 spawn**，会触发一轮 MSBuild 评估（源码没变是快速路径，变过就是真编译；2026-10-30 一次会话挂载留下 349 秒 CPU 的 `VBCSCompiler`，宿主被挤到没空响应，表现为页面卡住、按钮"检测中"）。**重服务请直接跑已编译产物**：`dotnet <…/bin/Release/<tfm>/<名称>.dll>`（实测零编译、约 1.8 秒就绪；改了源码先自己 `dotnet build -c Release`）。`npx <包>` 同理，首次还可能下载包 |
| 任务管理器里有多个命令行**相同**的 MCP 子进程，想知道各自属于哪个会话 | 看命令行的 `--project-mcp-session <会话 id>` 标记（stdio 服务器自动追加在 `.mcp.json` 的 `args` 之后）。同一份 `.mcp.json` 在多个会话下的其余命令行部分逐字相同，这段标记是唯一可区分归属的字段。命令见 [`development.md` 第 8.2 节](development.md#82-诊断分辨一个-mcp-子进程属于哪个会话) |
| 同一个会话起了**两个**命令行相同的子进程 | 不该再发生：挂载记账按 `agent.id`（会话 id）键控，同一会话被 `agent/created` 报告两次也只挂一次。若仍观察到，先确认运行进程加载的是新构建（Host 半边需重启 DSH 才生效）；仍复现则记录两个进程的 `ParentProcessId` 与启动时间，属于运行时观察 |
| HTTP 条目的服务没被自动拉起 | 见下"服务没被拉起"。先看 DSH 日志里有没有 `serve 配置已被忽略` / `serve 配置已被修正` / `没有 serve 配置` |
| 开了多个子代理后整段对话卡住 / 子代理会话打不开 / 输入区按钮永远「检测中」 | 见下"对话卡住（多子代理）"。这是 **2026-10-29 修复的缺陷**，先确认运行进程加载的是新构建（Host 半边换血走官方插件页删除 → 安装） |
| 点了 [启动]，工具没有立刻出现 | **正常**：`启动` 是异步动作，只保证授权写入完成并立刻返回 `accepted`；挂载在后台进行。看弹层该行是否从 `启动中` 走到 `已挂载`（见 [`behavior.md` §7.7](behavior.md#77-启动是异步动作accepted-语义)） |
| 打开会话很快，但 HTTP 条目的工具几分钟后才出现 | 新行为：会话创建不等 `serve` 就绪，等待改在后台挂载任务里。弹层显示 `启动中`；超时后仍会挂上（工具可能暂时不可用）。要缩短就自己常驻该服务 |
| 等满 120 秒、服务却没起来，`serve.command` 是 `pwsh` / `powershell` | **旧版本的已知缺陷，已修复**：Windows 上 `detached: true` 会变成 `DETACHED_PROCESS`（无控制台），PowerShell 在那种情形下立刻以退出码 0 结束、一行都不执行。现在 Windows 上对 PowerShell 不用 `detached`（其余命令仍用，否则服务会随宿主控制台一起死；见 [`design-http-serve.md` §4.3](design-http-serve.md)）。若仍复现，先确认运行进程加载的是**新构建**（Host 半边需重启 DSH） |
| 服务后来起来了，但那个会话里的工具始终不可用 | 该会话是在服务不可用时创建的：`mcp-client` 对 `streamable-http` **不会**在连不上之后自行恢复（已实测：服务健康、`/health/ready` 返回 200，同一会话仍报 `server is disconnected`）。**重开会话**即可；`serve` 的意义正是让"服务不可用"这件事尽量不发生 |
| 服务被拉起过，但 DSH 关掉后它还在跑 | 设计如此：`serve` 拉起的进程脱离 DSH 存活，生命周期归它自己。想结束就手动结束该进程 |
| 端口被别的进程占用，`serve` 没能拉起自己的服务 | 记一条 `拉起…的服务失败（错误类型：…）` 日志后照常挂载（可能连上那个别的实例）。本插件不检查端口归属、不抢占、不重试 |
| 明明写了 `serve`，日志却说"没有 serve 配置" | 该 `serve` 被丢弃了（畸形）。同一次会话创建里应有一条 `serve 配置已被忽略` 日志说明是哪个字段 |

## 按症状诊断

### 桌面版看不到按钮（Web 版正常）

**症状**：同一份 `.mcp.json`、同一个项目，Web 版（`dsh web`）的输入区有「项目 MCP」按钮，
桌面版（Electron）里没有；而同一插件的「工具调试」Tab 两边都在。看起来像"这个项目没有
项目级 MCP"。

**根因（旧构建）**：控制台路由当时用 boot 级 nonce 鉴权——`webServer.tapIndex()` 把
`<meta name="dsh-project-mcp-nonce">` 注入页面，路由校验 `x-project-mcp-nonce` 头。但桌面版的
**应用页面不经过 Host 渲染**：`apps/desktop/src/main.ts` 的 `protocol.handle` 用
`serveWebDocument()` 直接读打包 dist 的 `/`、`/index.html`、`/assets/*`，只额外注入 boot
脚本；结构化注入行走 IPC（desktop-host 在 ready 消息里发 `collectIndexInjections(peer)`）。
而 `packages/host/webserver` 的 `renderIndex()`（含 `applyIndexTaps`）**只有 Web 版的
frontend-static 走这条路**，`collectIndexInjections()` 又只收结构化 rows、不含 `tapIndex` 的
原始变换。于是 `tapIndex` 在桌面版**永不执行** → 页面里没有那个 meta → Client 读到空串 →
`GET /project-mcp/status` 一律 403 → `view=null` → 按钮直接不渲染。调试台不用 nonce，
所以它照常可用——这就是"只有按钮不见"的原因。

**判据**：`GET /project-mcp/status` 返回 **403** 即命中本问题（浏览器 DevTools 的 Network 里
能直接看到；或在本机用下面的命令探测）。**端口按实际值替换**：Web 版默认 `3080`；桌面版
端口由系统分配（`--port 0`，旧版曾固定 `19387`），从桌面进程的 `DSH_WEB_URL` 环境变量或
它的监听端口取，不要写死。`<会话 id>` 换成页面地址里的会话 id。

```powershell
curl.exe -s -o NUL -w "%{http_code}" "http://127.0.0.1:<端口>/project-mcp/status?session=<会话 id>"
```

这条只打印状态码（`403` / `400` / `200`）。

判读：**403** → 命中本问题；**400**（`missing-session`）→ 围栏已经通过，只是没带会话参数；
**200** → 路由与准入都正常，问题在别处（会话不可寻址时 `view` 为空，见
[`behavior.md`](behavior.md) §7.3）。

**修复**：控制台路由已改为**同源三重围栏**（与本插件「工具调试」Tab 完全同一套，唯一实现是
`src/same-origin.ts` 的 `requestAllowed`），不再读 nonce、也不再注册 `tapIndex`（2026-10-28）。
带该修复的构建上桌面版与 Web 版行为一致：按钮正常渲染，`/project-mcp/status` 不再因缺少
页面注入而 403。修复要真正生效，运行进程必须加载新构建（Host 半边换血走官方插件页
删除 → 安装，见上文快速分流第 3 条）；磁盘上的 `lib/` 不是运行时生效的证据。

### 工具没出现

按顺序排除：

1. **未授权**：弹层里该行是 `未授权`。点该行的 [启动]——授权这台服务器的当前配置并立即
   挂进当前会话，无需重开。
2. **配置哈希变了**：文件在批准后被改动过（该条目）。重新点 [启动]。这是刻意的安全属性
   ——没有它，"启动一次"就会永久授权该名字下未来的任何内容，包括 `git pull` 拉进来的
   恶意条目。
3. **与全局行撞名**："已跳过"里会写明。项目侧不挂载是有意选择：agent 作用域的同名
   服务器会静默遮蔽全局的，还会多 spawn 一个子进程。
4. **传输不支持**：`sse` / `ws` / `sdk` 一律跳过。把服务器换成 `streamable-http` 或
   `stdio`。
5. **变量缺失**：诊断只报变量名（不报值）。补上环境变量或用 `${VAR:-默认值}`。
6. **规范化后重名**：同一文件里两个键规范化后同名，先到者胜，后者跳过。改名即可。
7. **文件里根本没有可用服务器**：状态会显示 `已批准，但这份文件没有可挂载的服务器`，
   逐条原因在"已跳过"里。若一条都没声明，会显示 `（.mcp.json 里没有声明任何服务器。）`
8. **后台挂载还没落定**：挂载不等待 MCP 连接（会话秒开的代价），配了 `serve` 的 HTTP 条目
   还可能正在等自己的服务就绪。弹层显示 `启动中` 就是这种情况；落定后工具在下一轮出现。
   若长时间停在 `启动中`，按"等很久"排查服务本身。

### 连接失败

- 挂载设了 `failOnStartupError: false`：坏服务器只记日志，**不影响会话创建**。
- 诊断入口是 DSH 日志里的 `project-mcp：项目级 MCP 服务器「<名称>」启动失败：…`。
- 手工验证配置：`stdio` 的 `command` 与 `args` 能否在会话工作区里直接执行；`streamable-http`
  的 `url` 能否访问，`headers` 里的凭据是否有效。
- 变量展开问题表现为**服务器被跳过**（不是连接失败）：诊断会明确报变量名。
- `env` 是**附加**环境变量，不是替换：服务器进程继承宿主环境再叠加这里给出的键。
  依赖宿主环境变量却没继承到，通常是宿主进程本身没有该变量。

### 服务没被拉起

配了 `serve` 的 HTTP 条目在健康检查失败时会自动拉起服务。**如果它没被拉起**，按顺序排除：

1. **先确认这一步本该发生**：健康检查成功（服务已经在跑）时插件**完全不碰 `serve`**——不
   spawn、不记日志。所以"没有拉起"的最常见原因是**服务本来就在跑**。
   手工确认：`Invoke-WebRequest <health 地址>` 返回 2xx 就是这种情况，无需处理。
2. **该条目有 `serve` 吗**：没有 `serve` 时插件只能记一条
   `…且该条目没有 serve 配置，无法自动拉起服务` 日志，然后交给 `mcp-client` 自己重连。
3. **`serve` 被丢弃了吗**：`serve` 畸形时**只丢弃 `serve`**，服务器照常挂载（这是有意
   的：辅助配置写错不该让整个服务器不可用）。查 DSH 日志里有没有
   `serve 配置已被忽略：…`——它后面会写明是哪个字段。常见成因：
   - 缺 `command` 或 `command` 不是字符串；
   - `args` 不是字符串数组、`env` 不是"字符串 → 字符串"对象；
   - `health` 不是 `http://` / `https://` 开头（`file:` / `data:` / `ws:` 一律拒绝）；
   - 省略了 `health` 且 `url` 不是合法 http(s) 地址 → 推导不出健康端点；
   - `command` / `args` / `env` / `health` 里的 `${VAR}` 未定义且无默认值。
4. **`spawn` 失败了吗**：日志里会有 `拉起…的服务失败（错误类型：…）`。`command` 必须是
   **可执行文件名或绝对路径**（不经 shell 解释，因此 `"node script.js && something"`
   这种写法无效，管道、重定向、通配符也都不生效）。`Error` 的 `code` 不在日志里（红线 3：
   诊断不含配置内容），必要时在终端里手动跑一遍同样的命令。

   **还有一种"`spawn` 成功但子进程什么都没做"**：子进程立刻以退出码 0 结束、一行都不执行，
   日志里只剩一条"等待就绪超时"。历史上在 Windows 把 `serve.command` 写成 `pwsh` /
   `powershell` 就会这样——`detached: true` 在 Windows 上被实现成 `DETACHED_PROCESS`（子进程
   没有控制台），而 PowerShell 在那种情形下直接退出。**已修复**（Windows 上对 PowerShell 不用
   `detached`，逐项实验见 [`design-http-serve.md` §4.3](design-http-serve.md)）；仍复现就按第 6 条
   确认运行进程加载的是新构建。
5. **端口被别的进程占用**：同上一条的表现（`spawn` 成功但服务自己立刻退出）。本插件不检查
   端口归属、不抢占——它照常把条目交给 `mcp-client`，可能连上那个别的实例。
6. **新构建没进运行进程**：Host 半边没有热通道，`npm run build` 不会进入长跑进程。磁盘上
   的 `lib/serve.js` 不是运行时生效的证据，需要使用者重启一次 DSH。
7. **服务起来了，但 DSH 一关它也没了**：Windows 上这是**控制台耦合**。`serve.command` 不是
   PowerShell 时插件用 `detached`（服务不挂宿主控制台，能独立存活）；是 PowerShell 时不用
   `detached`（否则 pwsh 一行都不执行），此时服务能否独立存活取决于**启动脚本怎么创建它**：
   `Start-Process -WindowStyle Hidden` 创建的进程没有控制台，因此存活（已实测）；把服务直接跑
   在脚本前台就会随宿主控制台一起结束。要独立存活，就让启动脚本转手创建服务，或把
   `serve.command` 换成服务的可执行文件本身（例如 `dotnet <dll>`）。

**为什么非法 `health` 时宁可不拉起**：健康检查是拉起的唯一前提。没有可用的健康端点就永远
判不出"服务已经在跑"，于是每次会话挂载都会盲目拉一次，重复实例只能靠端口占用失败收场，
而那条失败是静默的（服务以 `stdio: 'ignore'` 启动，拿不到任何输出）。

### 对话卡住（多子代理）

**症状**：一次开了一批子代理（或并排几个会话）之后，**整段对话卡住**；子代理的会话内容
一直加载不出来；输入区的「项目 MCP」按钮永远显示「检测中」，点开也没有内容。

**根因（旧构建，2026-10-29 修复）**：两个缺陷叠加，且都由**一个带 `serve` 的 HTTP 条目
在等自己的服务就绪**引发：

1. `agent/created` 的监听器把挂载的 promise **返回给 Cordis 的 serial 派发**，而宿主会
   await 监听器返回值——于是**会话创建**被按在一个外部服务的启动上，最长 `readyTimeoutMs`
   （默认 120 秒）。子代理会话因此整批排在这个等待后面。
2. 控制台的 `status` 轮询当时没有单飞、没有超时、没有退避。服务端一慢，挂起的
   `GET /project-mcp/status` 按 1.5 秒的节奏累积，把该页面的**同源连接**占满——会话数据、
   子代理会话内容、按钮状态一起排队，于是"整个 GUI 卡住"。

**判据（按代价从低到高）**：

1. **搜 DSH 日志里的 `等待就绪超过`**。旧构建上，这条日志前面的那次**会话创建/恢复**就是
   被它拖住的那个（宿主 await 监听器返回值）；新构建上它只意味着"该条目的工具晚出现"，
   会话本身早就打开了。

与等待相关的日志一共四种，逐字如下（`<名称>` 是规范化后的服务器名）：

| 日志 | 含义 |
| --- | --- |
| `project-mcp：已拉起项目级 MCP 服务器「<名称>」的服务，但等待就绪超过 <readyTimeoutMs> 毫秒仍未就绪；仍交给 mcp-client 自行重试` | 服务起来了但健康端点没在上限内变 2xx（**`等待就绪超过` 就出现在这条**） |
| `project-mcp：项目级 MCP 服务器「<名称>」的健康端点未就绪（<原因>），且该条目没有 serve 配置，无法自动拉起服务；仍交给 mcp-client 自行重试` | 健康检查失败且该条目没写 `serve`，无从拉起 |
| `project-mcp：拉起项目级 MCP 服务器「<名称>」的服务失败（错误类型：<类型名>），仍交给 mcp-client 自行连接` | `spawn` 失败（命令不存在、端口占用等） |
| `project-mcp：后台挂载项目级 MCP 服务器失败（错误类型：<类型名>）` | 本次修复新增：后台挂载任务意外抛出（不应发生，出现即为缺陷） |

`<原因>` 是这四种之一：`健康端点地址非法` / `探测超时` / `健康端点返回 <状态码>` /
`无法连接健康端点`。日志里**没有** `.mcp.json` 内容、没有展开后的环境变量值。
2. **看 Network 里 pending 的请求**：浏览器 DevTools → Network，过滤 `project-mcp`。
   同时有多条 `status` 挂在 pending（旧构建按 1.5 秒节奏叠加）即命中。新构建同一时刻至多
   一条在途，且会在超时后 abort。
3. **确认运行进程加载的是新构建**：Host 半边没有热通道，`npm run build` 不会进入长跑进程。
   走官方插件页**删除 → 安装**（免重启，已实测）；`set_plugin` 停用→启用来回复用旧模块。
   磁盘上的 `lib/` 不是运行时生效的证据。

**修复后的行为**：会话创建路径**不等**任何 MCP 动作；挂载（含 `serve` 的就绪等待）在后台
任务里进行；[启动] 立即返回 `accepted`；轮询有单飞、超时、退避与可见性边界；服务端视图有
短 TTL 缓存。语义见 [`behavior.md` §7.6](behavior.md#76-轮询节奏与请求边界) 与
[§10](behavior.md#10-挂载语义)，实现约束见
[`development.md` 第 10 节](development.md#10-实现约束会话创建路径后台挂载与控制台轮询)。

### 等很久（HTTP 条目的工具迟迟不出来）

**打开会话本身不再等待**（2026-10-29 起）：会话立即创建，`serve` 的就绪等待发生在后台
挂载任务里。所以"打开一个会话要等一两分钟"**不该**在新构建上出现——真出现了按上一节
"对话卡住（多子代理）"诊断（那是旧构建的行为）。

现在能观察到的慢，是**该条目的工具晚出现**。按顺序排除：

1. **服务进程在跑吗**：`Get-CimInstance Win32_Process` 找 `command` 对应的进程
   （见 [`development.md` 第 8.3 节](development.md#83-诊断serve-为什么没把服务拉起来)）。
   - 进程在跑且 CPU 在动 → 在建索引，等就是了（弹层显示 `启动中`）；
   - 进程不在 → `spawn` 失败或服务立刻退出了。看服务自己的输出（本插件不代传它的输出：
     `stdio: 'ignore'` 是有意的，否则 DSH 退出时子进程会撞上 EPIPE）。
2. **健康端点对吗**：`health` 省略时用 `url` 的 **origin** + `/health/ready`。若服务实际的
   就绪路径不是这个，写显式 `health`。
3. **调大上限**：首次建索引特别慢时把 `readyTimeoutMs` 调大（上限 30 分钟，超过会被收敛并
   记一条 `serve 配置已被修正` 日志）。注意上限只约束**后台等待**，不再影响会话创建。
4. **改完 `.mcp.json` 必须重新批准该条**：被改条目的配置哈希变了（[`behavior.md` 第 6.2 节](behavior.md#62-配置哈希语义)），
   否则改动不生效——"改了配置却没有任何变化"通常就是这个原因。注意粒度：只有被改的那台
   回到 `未授权`，其他服务器的批准不受影响。
5. **等待只影响该条目**：同一会话里其余服务器（尤其是 stdio 条目）照旧立即挂上。若**所有**
   服务器都没挂上，那不是 `serve` 的问题，回到控制台弹层按"工具没出现"排查。
6. **已经在跑的服务零等待**：健康检查成功时插件完全不碰 `serve`。长期使用的服务由用户自己
   常驻启动最省事（`serve` 只是"没在跑时拉一把"的兜底）。

### 信任文件损坏

信任文件是 `${DSH_HOME:-~/.dsh}/project-mcp-trust.json`。任何异常情形（文件缺失、
JSON 损坏、`version` 不是 `2`（含 v1 旧文件，**不迁移**）、`projects` 不是对象、任一项目或
服务器条目结构不符）都**失败关闭**为"全部未信任"：

- 插件不会抛异常、不阻止 DSH 启动；
- 所有项目都显示 `未授权`，在控制台重新点 [启动] 即可；
- 文件会被下一次批准**整体重写**（原子写 + 权限 `0600`，v2 格式），因此损坏状态会自愈。

若怀疑是**并发写**（多个 DSH 进程同时批准不同项目），理论上存在锁外读导致的丢更新。
重新批准受影响的服务器即可；这不是数据损坏。

### 想撤销批准

弹层里该行点 **[撤销授权]**。行为：删除**该服务器**的批准记录（同项目其他服务器的记录
不受影响），并卸载本会话已挂载的对应实例。没有批准记录时该动作如实返回失败，不会误删。

- 撤销只影响当前项目根。换个工作区（或在含 `.git` 的父目录下工作）会命中另一个项目键。
- 撤销后想恢复：点该行的 [启动] 重新授权即可。
- 想彻底清除所有项目的批准记录：在确认没有其他项目仍需该记录后，自行删除
  `${DSH_HOME:-~/.dsh}/project-mcp-trust.json`。卸载插件**不会**删除它。
- 撤销后想立刻重新批准：卸载是异步的，紧接着的 [启动] 可能撞上尚未完成的卸载
  （`mcp-client` 的同作用域重名守卫会抛错，表现为"启动成功但没挂上"）。稍等片刻再点，
  或重开会话。

### 已知局限 被禁用的全局行仍占名

症状：某项目服务器被跳过，原因是"与全局 MCP 行同名，已被全局配置提供"，但工具列表里
**并没有**那个全局服务器。

原因：撞名检测只看行的模块名与 `serverName`，不看该行是否 `disabled: true`。一条被禁用的
全局行仍会占住名字，于是项目侧跳过、全局侧不连接——两边都不挂载。

处理：

- 给项目服务器换一个不与禁用行同名的键；或
- 启用/删除那条全局行；或
- 把该服务器直接写进 `.mcp.json` 并使用一个不冲突的名字。

修法（尚未实施）：只判 `entry.options.disabled === true` 字面量。**不能**读条目的
`disabled` getter——它会对 `!!js` 表达式求值（`new Function` + `eval`），在会话创建路径上
执行用户配置的 JS。

### 系统提示词里出现了 MCP 内容

**不该发生**（G4：本插件在任何计划状态下都不注入系统提示）。若在提示词里看到"待批准"、
"本会话未启用任何项目级 MCP"之类文本，说明运行进程加载的是旧构建——Host 半边换血走
官方插件页删除 → 安装，重启复查。核对口径见
[`behavior.md` 第 9 节](behavior.md#9-不注入系统提示g4)。

诊断信息（跳过原因、重命名、文件为空）**不会**进入系统提示词——它们只在控制台弹层里。
这是刻意的：提示占用模型上下文，而按钮不占用。

## 运行时观察目标

排查时按这张表核对，而不是只看配置文件：

| 观察点 | 期望 |
| --- | --- |
| Loader 行 | 有且仅有一条 `dsh-project-mcp`（插件自身的行） |
| 项目级 MCP 行 | **不出现**在 Loader 里——项目服务器按会话挂在 agent 作用域，不在 profile 树里 |
| 工具面 | 已批准的项目服务器提供 `mcp__<规范名>__<工具名>` |
| 全局行 | 若 profile 里仍有 MCP 行，它们与项目服务器是两套；它们挂载得比任何会话都早 |
| 控制台面 | 输入区按钮渲染（Client 半边已供应）、`/project-mcp/status?session=…` 对同源请求返回 200。准入是**同源三重围栏**（与调试台共用 `src/same-origin.ts`），**不依赖任何页面注入**；403 说明围栏拒绝，400 说明围栏已过但缺会话参数 |
| 信任文件 | `${DSH_HOME:-~/.dsh}/project-mcp-trust.json`，权限 `0600`，**version 2**，不含 `.mcp.json` 内容 |
| `serve` 拉起的服务进程 | 命令行 = `serve.command` + `serve.args`（**没有** `--project-mcp-session` 标记——那是 stdio 条目的子进程才有的），父进程已退出或与 DSH 无关 |
| DSH 进程自身 | 不在 Windows Job 对象里（脱离能生效的前提）；若被放进 Job（如由 IDE 或计划任务启动），服务可能随 DSH 退出。脱离手段按平台与命令不同：POSIX 用 `detached`；Windows 上对 PowerShell **不用**（用了会让它静默空转），其余命令仍用，见 [`design-http-serve.md` §4.3](design-http-serve.md) |
| 控制台轮询 | 同一时刻**至多一条** `GET /project-mcp/status` 在途；页面隐藏时**没有**请求；连续失败时间隔按指数增大。同时看到多条 pending 说明跑的是旧构建 |

## 未验证项

以下需要真实 DSH profile 与会话，尚未验证；排查时**不要**把它们的当前行为当成已确认：

- `agent/created` 在 `clear` / `compact` source 下的幂等性；
- 非阻塞挂载下 fiber 在 agent dispose 时的清理时机；
- 从 `agent.ctx` 遍历 Loader 树能否拿到完整条目集；
- 首条消息是否真的赶不上工具注册（2026-10-29 起，HTTP 条目还可能因为后台挂载而更晚一轮）；
- 控制台按钮与弹层在真实 GUI 会话中的渲染与交互（本环境无浏览器控制；桥接路由已用
  假 req/res + 真实 HTTP 双路实测）；
- **DSH 进程整体退出后，由 `serve` 拉起的服务是否存活**（`detached + unref` 能让服务脱离
  直接父进程已实测，但"Dsh 退出"这条只能等真实会话验证）；
- **真实 MudMCP 首次建索引的耗时分布**（默认 120 秒的依据是"实测可能超过 90 秒"这一次
  观测，不同项目/机器上合适的值可能不同）；
- **Windows + PowerShell 路径下，宿主控制台里的 Ctrl+C 具体多久之内带走服务**（"父进程退出、
  控制台拆除后，直接 spawn 的服务会消失；由 `Start-Process -WindowStyle Hidden` 创建的服务
  存活"都已实测，但 Ctrl+C 这一具体触发方式与其时间窗未单独测量）；
- **`mcp-client` 对 `streamable-http` 是否还有更长的重连预算**：已实测"服务不可用时创建的
  会话，在服务恢复健康后仍报 `server is disconnected`"（单次观察，未做长时间跟踪）；
- **后台挂载落定与 `agent/created` 返回之间的竞态**：挂载已移出创建路径，但"创建返回后多久
  工具出现"只有单元级证据（夹具 + 可控 promise），真实会话里的时序未测量。

**已证实（不再列为未验证）**：`agent/created` 的 serial 派发**确实**会 await 监听器的返回值
——2026-10-29 现场确认：把挂载 promise 返回给宿主，等于把会话创建按在 `serve` 的就绪等待上
（最长 `readyTimeoutMs`），多开子代理时表现为整段对话卡住。因此该等待已移出创建路径。
