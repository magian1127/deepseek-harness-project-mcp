# 故障排查（troubleshooting）

> 本文件只负责"症状 → 诊断动作"。用户可见语义与失败模式见 [`behavior.md`](behavior.md)；
> 实现约束见 [`development.md`](development.md)；设计依据见 [`design.md`](design.md)。

## 快速分流

1. **先跑 `/mcp-project`**。它是诊断项目级 MCP 的唯一入口：项目路径、状态、已挂载、
   未批准、已跳过（含原因）、规范化重命名都在这一条输出里。
2. 再看**会话提示**。提示只在两件事上出现：`.mcp.json` 无法使用（无法解析，或超过
   1 MiB 被拒读），或有可挂载项但未批准。
   没有提示**不代表没问题**——跳过类问题不注入提示。
3. 确认运行中的进程加载的是新构建。Host 半边**没有热通道**，`npm run build` 不会进入
   长跑进程；需要由使用者重启一次 DSH 后复查。磁盘上的 `lib/` 不是运行时生效的证据。
4. 全程不要用"重启 DSH"代替诊断，也不要自行编辑受管 profile 行。

## 症状索引

| 症状 | 最短诊断路径 |
| --- | --- |
| 项目服务器一个都没挂上 | `/mcp-project` 看"状态"行。`尚未批准` → 批准；`未启用：…` → 看"已跳过"逐条原因；`已批准，但这份文件没有可挂载的服务器` → 见下 |
| 工具列表里没有 `mcp__<名称>__*` | 先确认已批准（`/mcp-project`）；再看该服务器是否出现在"已跳过"里；最后确认首条消息可能赶不上工具注册，下一轮再看 |
| 明明批准过，重开会话又要批准 | 指纹变了——`.mcp.json` 内容有任何改动（含 `git pull` 拉入新条目）都会失配。这是设计行为，见 [`behavior.md` 第 6.2 节](behavior.md#62-指纹语义) |
| 某个服务器被跳过，原因写着"与全局 MCP 行同名" | 该项目服务器与 profile 里的全局行撞名，项目侧不挂载。若那条全局行是 `disabled: true` 的，属于已知局限，见下 |
| 某个服务器被跳过，原因写着"不支持的传输类型" | `.mcp.json` 里写了 `sse` / `ws` / `sdk`。DSH 只支持 `stdio` 与 `streamable-http`（`http` 是别名） |
| 某个服务器被跳过，原因写着"变量 X 未定义且无默认值" | 该环境变量在 DSH 进程的环境里不存在。用 `${X:-默认值}` 提供回退，或在启动 DSH 的环境里设置它 |
| 某个服务器被跳过，原因写着"条目含 url 但没有 type" | 补上 `"type": "http"`（或 `"streamable-http"`） |
| 服务器名与预期不符，工具名前缀是 `mcp__my_server_ab12cd34__*` | 键名含 `[A-Za-z0-9_-]` 以外的字符，被规范化重命名。`/mcp-project` 的"规范化重命名"给出原名 → 规范名 |
| 批准时报"未知的服务器名" | 只能用**规范化后**的名字批准（照 `/mcp-project` 或会话提示列出的抄）。原名含非法字符时不能直接用作批准名 |
| 批准成功但本会话没有挂载 | 该服务器被跳过（撞名 / 传输不支持 / 变量缺失 / 重名）。`/mcp-project` 的"已跳过"给出原因 |
| 已经批准了，系统提示里还写着"尚未批准" | 不该再发生：`trust` / `untrust` 都会按新计划刷新提示段（[`behavior.md` 第 10.1 节](behavior.md#101-批准后当前会话的状态)）。若仍观察到，说明运行进程加载的不是新构建（Host 半边需重启 DSH 才生效），先重启复查 |
| 已批准，但工具列表里没有 `mcp__<名称>__*` | 若是**别的会话**批准后本会话才打开：挂载只发生在会话创建时或本会话自己执行 `trust` 时，本会话的计划虽已是"已批准"但一个都没挂。`/mcp-project` 会把它列在"已批准但本会话未挂载"下——运行 `/mcp-project trust` 即挂上 |
| 服务器已挂载但工具报连接失败 | MCP 服务器自身的启动或握手失败。挂载刻意不等待连接（会话秒开），失败只记日志，不影响会话。**该服务器会立即从挂载记账移除**，`/mcp-project` 不再把它列为"已挂载"，而是列在"已批准但本会话未挂载"下。查 DSH 日志与该服务器的 `command` / `url` 是否可手动执行 |
| 会话里没有 `/mcp-project` 命令 | 该 profile 不提供 `commands` 服务（例如 `sdk-minimal`），插件保持未激活；或新构建尚未进入运行进程（需重启 DSH）。查 DSH 日志里的 `project-mcp：宿主没有 commands 服务` 警告 |
| 会话里没有 `/mcp-project` 命令，但日志没有上面那条警告 | 命令未注册且无诊断。`inject` 已声明 `commands`，按声明语义插件此时应保持未激活（连同命令与提示一起不生效），而不是"插件活着但没有命令面"——若观察到后者，说明该 profile 的 `commands` 服务在 `apply` 之后才卸载或未按声明供给，请记录为运行时观察 |
| 会话提示里出现"无法解析" | `.mcp.json` 不是合法 JSON、顶层不是对象，或 `mcpServers` 不是对象。修文件后运行 `/mcp-project` 复查 |
| 会话提示或 `/mcp-project` 里出现"过大" | `.mcp.json` 超过 1 MiB，被**拒读**（没读进内存，也没挂载）。诊断会给出实测大小与上限。这是有意的尺寸闸门：读盘在会话创建的同步路径上，无上限会让陌生仓库里的异常大文件拖住会话创建。精简该文件（真实的 `.mcp.json` 只需声明服务器列表，远小于 100 KiB）后重新批准 |
| 提示"尚未批准"但我不想批准 | 不用做任何事——不批准就不连接、不 spawn 进程。想让提示消失就批准该项目的服务器，或把 `.mcp.json` 移出项目根 |
| 批准后想撤销 | `/mcp-project untrust`：撤销该项目批准并卸载本会话已挂载的项目服务器 |
| 撤销后重新批准没有生效 | 确认 `.mcp.json` 仍在原路径、指纹未变；`/mcp-project` 应显示"尚未批准"。若仍显示旧状态，确认运行进程加载的是新构建 |
| 信任文件损坏，所有批准都丢了 | 失败关闭行为：文件缺失、JSON 损坏、版本号不认识、条目结构不符 → 一律视为全部未信任。重新批准即可；插件不会阻止 DSH 启动 |
| 克隆陌生仓库后担心被自动执行 | 不会。批准记录只存在于 `${DSH_HOME:-~/.dsh}`，项目内没有可写入的批准通道；未批准时既不 spawn 进程也不发起网络连接 |
| 子代理会话里没有项目 MCP | 设计如此：子代理（`origin === 'subagent'`）与父会话共享工作区，不重复建连接与子进程。**分叉会话（fork）不属于此列**——它带 `parentSession` 但无 `origin`，是独立会话，照常挂载 |
| 多个会话各起了一份子进程 | 设计如此：项目级服务器按会话独立连接，N 个会话 = N 份连接与子进程。要单份就放进 profile 的全局行 |
| 任务管理器里有多个命令行**相同**的 MCP 子进程，想知道各自属于哪个会话 | 看命令行的 `--project-mcp-session <会话 id>` 标记（stdio 服务器自动追加在 `.mcp.json` 的 `args` 之后）。同一份 `.mcp.json` 在多个会话下的其余命令行部分逐字相同，这段标记是唯一可区分归属的字段。命令见 [`development.md` 第 8.2 节](development.md#82-诊断分辨一个-mcp-子进程属于哪个会话) |
| 同一个会话起了**两个**命令行相同的子进程 | 不该再发生：挂载记账按 `agent.id`（会话 id）键控，同一会话被 `agent/created` 报告两次也只挂一次。若仍观察到，先确认运行进程加载的是新构建（Host 半边需重启 DSH 才生效）；仍复现则记录两个进程的 `ParentProcessId` 与启动时间，属于运行时观察 |
| **工具突然消失**（之前能用，现在 `mcp__<名称>__*` 不见了） | **很可能是被回收了**——超过连接上限（默认 8）时，插件会回收**最久未活跃的空闲会话**的连接。先跑 `/mcp-project` 看是否显示"本会话的连接已被回收"；**发一条消息即自动重挂**（该次请求看不到新工具，下一轮可见）。详见下节 |
| 子进程数量没随回收下降 | 回收调的是 `fiber.dispose()`（唯一能停掉连接的方式，因为 `mcp-client` 会自动重连、杀进程会被重新拉起）。若进程仍在，先确认运行进程加载的是新构建（Host 半边需重启 DSH 才生效），再核对 `--project-mcp-session <会话 id>` 标记定位归属（见 [`development.md` 第 8.2 节](development.md#82-诊断分辨一个-mcp-子进程属于哪个会话)） |

## 按症状诊断

### 工具没出现

按顺序排除：

1. **未批准**：`/mcp-project` 的"状态"是 `尚未批准，本会话未挂载任何项目级 MCP`。
   运行 `/mcp-project trust`（整个文件）或 `/mcp-project trust <名称>…`（按名）。
   批准后立即挂进当前会话，无需重开。
2. **指纹变了**：文件在批准后被改动过。重新批准。这是刻意的安全属性——没有它，
   "批准一次"就会永久授权该路径下未来的任何内容，包括 `git pull` 拉进来的恶意条目。
3. **与全局行撞名**："已跳过"里会写明。项目侧不挂载是有意选择：agent 作用域的同名
   服务器会静默遮蔽全局的，还会多 spawn 一个子进程。
4. **传输不支持**：`sse` / `ws` / `sdk` 一律跳过。把服务器换成 `streamable-http` 或
   `stdio`。
5. **变量缺失**：诊断只报变量名（不报值）。补上环境变量或用 `${VAR:-默认值}`。
6. **规范化后重名**：同一文件里两个键规范化后同名，先到者胜，后者跳过。改名即可。
7. **文件里根本没有可用服务器**：状态会显示 `已批准，但这份文件没有可挂载的服务器`，
   逐条原因在"已跳过"里。若一条都没声明，会显示 `（.mcp.json 里没有声明任何服务器。）`
8. **首条消息赶不上工具**：挂载不等待 MCP 连接（会话秒开的代价）。下一轮消息再看。

### 连接失败

- 挂载设了 `failOnStartupError: false`：坏服务器只记日志，**不影响会话创建**。
- 诊断入口是 DSH 日志里的 `project-mcp：项目级 MCP 服务器「<名称>」启动失败：…`。
- 手工验证配置：`stdio` 的 `command` 与 `args` 能否在会话工作区里直接执行；`streamable-http`
  的 `url` 能否访问，`headers` 里的凭据是否有效。
- 变量展开问题表现为**服务器被跳过**（不是连接失败）：诊断会明确报变量名。
- `env` 是**附加**环境变量，不是替换：服务器进程继承宿主环境再叠加这里给出的键。
  依赖宿主环境变量却没继承到，通常是宿主进程本身没有该变量。

### 信任文件损坏

信任文件是 `${DSH_HOME:-~/.dsh}/project-mcp-trust.json`。任何异常情形（文件缺失、
JSON 损坏、`version` 不是 `1`、`projects` 不是对象、任一项目条目结构不符）都**失败关闭**
为"全部未信任"：

- 插件不会抛异常、不阻止 DSH 启动；
- 所有项目都显示"尚未批准"，重新批准即可；
- 文件会被下一次批准**整体重写**（原子写 + 权限 `0600`），因此损坏状态会自愈。

若怀疑是**并发写**（多个 DSH 进程同时批准不同项目），理论上存在锁外读导致的丢更新。
重新批准受影响的项目即可；这不是数据损坏。

### 想撤销批准
```text
/mcp-project untrust
```

行为：撤销**该项目**的批准记录（其他项目不受影响），并卸载本会话已挂载的项目服务器。
没有批准记录时也会清理本会话的挂载。

- 撤销只影响当前项目根。换个工作区（或在含 `.git` 的父目录下工作）会命中另一个项目键。
- 撤销后想恢复：`/mcp-project trust` 重新批准即可。
- 想彻底清除所有项目的批准记录：在确认没有其他项目仍需该记录后，自行删除
  `${DSH_HOME:-~/.dsh}/project-mcp-trust.json`。卸载插件**不会**删除它。
- 撤销后想立刻重新批准：`dispose()` 是异步的，紧接着的 `trust` 可能撞上尚未完成的卸载
  （`mcp-client` 的同作用域重名守卫会抛错，表现为"批准成功但没挂上"）。稍等片刻再批准，
  或重开会话。

### 工具突然消失（很可能被回收了）

症状：某个会话里项目级 MCP 的工具（`mcp__<名称>__*`）之前能用，现在不见了；会话本身
一切正常，`.mcp.json` 与批准记录都没动过。

**这是设计行为，不是故障。** DSH 的 WebUI 没有"关闭会话"，点开任意会话就会挂上一份
MCP 连接（每个 stdio 子进程约 73 MB），而 DSH 没有空闲回收机制。因此本插件在连接数
**超过上限（默认 8 个会话）**时，回收**最后活跃时间最早**的 `status === 'idle'` 会话的
连接。规则见 [`behavior.md` 第 10.2 节](behavior.md#102-连接的回收与上限)。

**怎么确认**：

```text
/mcp-project
```

看两行：

- `连接上限：8 个会话（当前记账 N 个）` —— 当前生效的上限与记账的会话数。
- `本会话的连接已被回收（…）` —— 本会话就是被回收的那个。

也可以在 DSH 日志里找这条（只含会话 id 与连接数量，不含任何配置内容）：

```powershell
Select-String -Path <DSH 日志> -Pattern '已回收最久未活跃的空闲会话'
```

**怎么恢复**：

| 情形 | 做法 |
| --- | --- |
| 只是想在当前会话继续用 | **直接发一条消息**——`agent/pre-step` 会自动重挂。注意**当次请求的工具列表仍是旧的**，**下一轮**才能看到工具 |
| 希望工具立刻可用、且不想等一轮 | 运行 `/mcp-project trust`（幂等，会立即挂载进当前会话） |
| 常用会话总被回收 | 调大上限：插件页的 `connectionLimit`（默认 8）。或在 profile 行 `dsh-project-mcp` 的 `config` 里设置 |
| 不想有任何回收 | 把 `connectionLimit` 设成一个很大的数（如 1000） |
| 想立刻释放内存 | 回收只在"新会话挂载前 / 发消息 / 执行命令"时发生；要主动释放就重开一个会话（旧的空闲会话会被优先回收），或重启 DSH |

**排除其它原因**（工具消失也可能是这些）：

1. **从未挂上**：`/mcp-project` 的"状态"是"尚未批准"→ 批准；或列在"已批准但本会话未挂载"
   下 → `/mcp-project trust`。
2. **服务器被跳过**：看"已跳过"逐条原因（撞名 / 传输不支持 / 变量缺失 / 重名）。
3. **连接启动失败**：`/mcp-project` 会把它列在"已批准但本会话未挂载"下（启动失败的
   fiber 会立即从挂载记账移除）；日志里有"启动失败"。
4. **指纹变了**：`.mcp.json` 被改动（含 `git pull`）→ 重新批准。
5. **首条消息赶不上工具**：刚批准的会话，第一轮可能看不到工具，下一轮才有。
6. **运行进程加载的不是新构建**：Host 半边需重启 DSH 才生效。若观察到"日志里没有回收
   记录、命令也不显示被回收，但工具确实消失"，请按运行时观察记录。

**为什么全部在跑时不回收**：回收正在工作的会话会打断你正在进行的工作（连接被拆、当前轮
的 MCP 工具调用失败），代价远高于多占一份内存。因此 9 个会话都在 `running` 时**忽略
上限**，一个都不回收。

### 已知局限 被禁用的全局行仍占名

症状：某项目服务器被跳过，原因是"与全局 MCP 行同名，已被全局配置提供"，但工具列表里
**并没有**那个全局服务器。

原因：撞名检测只看行的模块名与 `serverName`，不看该行是否 `disabled: true`。一条被禁用的
全局行仍会占住名字，于是项目侧跳过、全局侧不连接——两边都不挂载。

处理：

- 给项目服务器换一个不与禁用行同名的键；或
- 启用/删除那条全局行；或
- 把该服务器直接写进 `.mcp.json` 并使用一个不冲突的名字。

修法（尚未实施）：只判 `entry.options.disabled === true` 字面量。**不能**读条目的
`disabled` getter——它会对 `!!js` 表达式求值（`new Function` + `eval`），在会话创建路径上
执行用户配置的 JS。

### 会话提示出现在不需要的地方

提示只应在两种情形出现：`.mcp.json` 无法使用（无法解析，或超过 1 MiB 被拒读）、或有可
挂载项但未批准。若在别的情形看到
提示，先确认运行进程加载的是新构建（Host 半边需重启 DSH 才生效），再核对
[`behavior.md` 第 9 节](behavior.md#9-会话提示只用于需要你行动的情形)。

**提示段与当前计划保持一致**：会话创建时按当时的计划注入，此后每次
`/mcp-project trust` / `untrust` 都会按新计划刷新（"先撤下、再重注入或留空"）。
批准之后旧提示不会残留，撤销之后待批准提示会出现（见
[`behavior.md` 第 10.1 节](behavior.md#101-批准后当前会话的状态)）。若观察到陈旧提示，
先确认运行进程加载的是新构建。

诊断信息（跳过原因、重命名、文件为空）**不会**进入会话提示——它们只在 `/mcp-project`
里。这是刻意的：提示占用模型上下文，只在用户需要做决定时才值得。

## 运行时观察目标

排查时按这张表核对，而不是只看配置文件：

| 观察点 | 期望 |
| --- | --- |
| Loader 行 | 有且仅有一条 `dsh-project-mcp`（插件自身的行） |
| 项目级 MCP 行 | **不出现**在 Loader 里——项目服务器按会话挂在 agent 作用域，不在 profile 树里 |
| 工具面 | 已批准的项目服务器提供 `mcp__<规范名>__<工具名>`；**被回收过的会话下一轮才恢复** |
| 全局行 | 若 profile 里仍有 MCP 行，它们与项目服务器是两套；它们挂载得比任何会话都早 |
| 命令面 | `/mcp-project` 可用（该 profile 提供 `commands` 服务时） |
| 信任文件 | `${DSH_HOME:-~/.dsh}/project-mcp-trust.json`，权限 `0600`，不含 `.mcp.json` 内容 |
| 连接数 | 空闲会话的连接**不超过上限（默认 8）**；全部在 `running` 时允许超出 |
| 子进程数 | 应随回收下降（`fiber.dispose()`）。用 `--project-mcp-session <会话 id>` 标记归属 |

## 未验证项

以下需要真实 DSH profile 与会话，尚未验证；排查时**不要**把它们的当前行为当成已确认：

- `agent/created` 在 `clear` / `compact` source 下的幂等性；
- 非阻塞挂载下 fiber 在 agent dispose 时的清理时机；
- 从 `agent.ctx` 遍历 Loader 树能否拿到完整条目集；
- 首条消息是否真的赶不上工具注册；
- `/mcp-project` 与提示段在真实 GUI 会话中的实际渲染；
- **`agent/pre-step` 是否对每个会话都触发**——重挂完全依赖它。若被回收的会话发消息后
  没有重挂，这是第一个要查的点（见 [`development.md` 第 8 节](development.md#8-验证分层与未验证项)）；
- **回收是否真的释放子进程**：测试只证明 `fiber.dispose()` 被调用，真实释放取决于
  `mcp-client` 在 dispose 时杀掉子进程；用任务管理器核对进程数是否下降；
- **`Config` 的插件页表单**：测试 profile 无 schemastery，只覆盖了降级为 `undefined` 的
  路径；有 schemastery 时的表单渲染与改值生效未经运行时验证。
